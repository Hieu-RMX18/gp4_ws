## 2. File-by-file review

### 2.1 CMakeLists.txt

**What it does:** Standard ament_cmake build with `ament_cmake_python`. Installs the
Python package, 6 scripts, and config/launch directories. Defines 6 pytest tests.

**Dependencies:** Only `ament_cmake` and `ament_cmake_python` as build tools.

**Issue:** No C++ components — this could be a pure `ament_python` package. The
ament_cmake wrapper adds unnecessary build complexity for a pure-Python package.

**W4 decision:** REDESIGN — use `ament_python` build type unless C++ components
are planned (unlikely for perception).

### 2.2 package.xml

**What it does:** Declares package `gp4_perception` with dependencies.

**Critical issue:** Depends on `gp4_interfaces` and test-depends on `gp4_safety`.
These package names do NOT exist on the current branch:
- `gp4_interfaces` → current name is `interfaces`
- `gp4_safety` → current name is `safety`

This would cause a build failure if checked out directly.

**Dependencies:** rclpy, geometry_msgs, sensor_msgs, diagnostic_msgs, ament_index_python.
All are standard and available in Humble.

**W4 decision:** REDESIGN — use current package names (`interfaces`, `safety`).
Add W4.T0 interface dependencies (CalibrateHandEye.srv, GetObjectPositions.srv, etc.).

### 2.4 config/d435i.yaml

**What it does:** Camera configuration for Intel RealSense D435i. Sets resolution
(640x480), FPS (30), enables color+depth, disables infra/gyro/accel. Defines topic
mappings and expected topic list. Sets clip_distance_m: 1.5.

**Frame conventions:** parent_frame: base_link, camera_frame: camera_color_optical_frame,
depth_frame: camera_depth_optical_frame.

**Quality:** Clean and well-structured. Topic paths follow RealSense ROS2 wrapper
conventions (`/camera/camera/...`).

**Issue:** `clip_distance_m: 1.5` is a hardcoded numeric — should be in the config
but the value needs validation against the actual workspace. Also `pointcloud_enable: false`
is reasonable as a default.

**W4 decision:** KEEP — update clip_distance if workspace geometry requires it.

### 2.7 config/vision_pick_planner.yaml

**What it does:** Configuration for vision-guided pick planning. Key settings:
- `runtime.enable_real_vision_pick: false` — safety gate, disabled by default
- `selection.min_confidence: 0.50` — object detection threshold
- `workspace_bounds` — defines valid pick volume in base_link frame
- `approach_policy` — pre-pick offset, approach/retreat vectors (all 10cm Z-axis)
- `orientation_policy` — TCP-down orientation with yaw strategy
- `reject_j5_near_zero_abs_rad: 0.0873` — ~5° singularity avoidance for J5

**Quality:** Well-structured. The safety gate pattern (enable_real_vision_pick=false)
is exactly right. Workspace bounds are explicit with frame_id.

**Issue:** `reject_j5_near_zero_abs_rad` is a joint-space safety parameter embedded
in a perception config. This arguably belongs in `safety/config/safety_rules.yaml`
per the SSOT rule.

**W4 decision:** KEEP values. Move `reject_j5_near_zero_abs_rad` to safety config.

### 2.8 gp4_perception/calibration_recorder_node.py

**What it does:** ROS2 node that subscribes to PoseStamped messages on
`/gp4_perception/fiducial_observation` and records them as YAML or CSV.
Does NOT solve the hand-eye transform — observation capture only.

**Parameters:** enabled (False), mock_mode (True), observation_topic,
output_directory (/tmp/...), output_format, robot_base_frame, robot_reference_frame.

**Calibration approach:** Records pairs of (camera-frame marker pose, robot FK pose)
for later offline solving. The node explicitly states it does NOT solve transforms.

**ROS interfaces:**
- Subscribes: PoseStamped on configurable topic (QoS = 10, default)

**QoS issue:** Uses QoS depth=10 (default). Should use `SensorDataQoS` or at least
`BEST_EFFORT` reliability to match RealSense publishers which use sensor QoS.

**Is calibration_date hardcoded?** No. The node doesn't write calibration_date at all.
It writes `calibration_status: False` and `transform_solved: False` in output YAML.

**Depth/freshness/reprojection guard?** No. The node accepts any PoseStamped without
checking timestamp freshness, coordinate validity, or measurement quality.

**Bugs:**
- `marker_id` is hardcoded as `"fiducial_marker_tbd"` — should come from the
  detection pipeline
- No validation that the received pose is finite or within reasonable bounds
- No deduplication of observations at the same robot configuration

**W4 decision:** REDESIGN. Keep the observation-recording pattern but:
1. Use typed CalibrationObservation message from W4.T0 interfaces
2. Add QoS matching (SensorDataQoS)
3. Add timestamp freshness guard
4. Add finite-value validation
5. Connect marker_id to actual fiducial detection output
6. Add a hand-eye solver (OpenCV solvePnP or similar)

### 2.9 gp4_perception/fiducial_detector_node.py

**What it does:** Subscribes to RGB images and CameraInfo topics. Currently a
skeleton — receives images but does NOT perform actual marker detection. Logs a
one-time warning that detection is not implemented.

**Parameters:** enabled (False), mock_mode (True), fiducials_config_file,
rgb_topic, camera_info_topic.

**TBD-aware config:** The `load_fiducial_config()` function correctly treats TBD
values as None and prevents the detector from claiming readiness when config is
incomplete. The `detector_runtime_state()` function provides clear diagnostic
messages for each state (disabled, mock, not-ready, ready).

**QoS:** Uses depth=10 (default) for Image and CameraInfo. Should match
RealSense QoS (SensorDataQoS = BEST_EFFORT + volatile).

**ROS interfaces:**
- Subscribes: sensor_msgs/Image on `/camera/camera/color/image_raw`
- Subscribes: sensor_msgs/CameraInfo on `/camera/camera/color/camera_info`
- Does NOT publish detected marker poses (skeleton)

**Bugs:**
- No actual detection implementation — this is the "not-finished-rebuild"
- QoS mismatch will cause the node to NOT receive messages from the real camera
- No depth image subscription (needed for 3D marker pose estimation)

**W4 decision:** REDESIGN. Keep the TBD-aware config pattern and runtime state
machine, but implement actual detection:
1. Add ArUco/ChArUco detection using OpenCV
2. Subscribe to depth image for 3D pose estimation
3. Use SensorDataQoS
4. Publish detected marker poses on typed topic
5. Add depth-noise guard (reject markers with high depth variance)
6. Add reprojection error check

### 2.10 gp4_perception/realsense_health_node.py

**What it does:** Periodically checks which RealSense topics are available and
publishes a DiagnosticArray. Evaluates camera health based on expected topics,
calibration status, and dry-run mode.

**Key design patterns:**
- Health check via topic existence (checks `get_topic_names_and_types()`)
- Dry-run safety: missing topics = WARN in dry-run, ERROR in non-dry-run
- Calibration awareness: reports `ready=True` only when topics available AND
  calibration_status=True
- Transition logging: only logs state changes, not every check cycle

**Parameters:** d435i_config_file, camera_extrinsics_file, dry_run (True),
status_topic, check_period_sec (1.0).

**ROS interfaces:**
- Publishes: diagnostic_msgs/DiagnosticArray on `/gp4_perception/realsense_health`
- No subscriptions (uses `get_topic_names_and_types()` for discovery)

**QoS:** Publisher uses depth=10. Acceptable for diagnostics.

**Quality:** This is the most complete and well-designed node in the package.
Clean separation of config loading, health evaluation, and ROS publishing.
The `CameraHealthResult` dataclass is well-structured.

**Issues:**
- `check_period_sec=1.0` polls every second — may want to be configurable for
  production vs development
- No depth quality assessment (could check camera info for valid intrinsics)

**W4 decision:** KEEP with minor updates. This node can be reused almost as-is.
Add depth quality metrics and optional alert escalation.

### 2.11 gp4_perception/vision_pick_planner.py

**What it does:** The most complex file (~600+ lines). Takes detected objects and
a target label, validates workspace bounds, computes approach/retreat waypoints,
applies orientation policy, and produces a structured pick plan.

**Key functions:**
- `select_pick_target()` — finds best matching object by label + confidence
- `check_workspace_bounds()` — validates position within configured volume
- `plan_approach_retreat()` — computes pre-pick, pick, and retreat poses
- `apply_yaw_strategy()` — fixed yaw or object-aligned yaw with delta limit
- Hardware block enforcement: always includes `hardware_execution_disabled` and
  checks `enable_real_vision_pick`, camera calibration, TCP readiness, gripper readiness

**Safety design:** Excellent. Multiple hardware block reasons are collected and
reported. The planner never claims hardware readiness unless ALL prerequisites
are met. `DetectedObjectRecord` tracks calibration status per object.

**Workspace bounds:** Uses a simple axis-aligned bounding box in base_link frame.
Adequate for a static table-top scenario.

**Orientation policy:** Supports fixed yaw and object-yaw strategies. Includes
`max_yaw_delta_rad` limit and J5-near-zero rejection.

**Dependencies:** Pure Python, no ROS dependencies in the core logic. Can be
tested without a ROS environment.

**Issues:**
- No ROS node — this is a library module, not a node. Needs a node wrapper
  or service interface for W4 integration
- `_hardware_block_reasons()` hardcodes `'hardware_execution_disabled'` as always
  present — correct for pre-hardware phase but needs a runtime gate
- No freshness check on detected objects (timestamp not validated)
- Quaternion normalization in `_quaternion4()` silently normalizes instead of
  rejecting far-from-unit quaternions

**W4 decision:** KEEP core logic. Wrap in a ROS service using W4.T0
GetObjectPositions.srv interface. Add:
1. Object freshness validation (reject stale detections)
2. Explicit quaternion validity check (reject norm < 0.9 or > 1.1)
3. Integration with actual perception pipeline output

## 3. Cross-cutting findings

### 3.1 QoS mismatch (affects all subscriber nodes)

All nodes use default QoS (depth=10, RELIABLE). RealSense ROS2 wrapper publishes
with `SensorDataQoS` (BEST_EFFORT, volatile, depth=5). This QoS mismatch means
**subscriber nodes will NOT receive camera messages** in a real deployment.

**W4 must fix:** Use `rclpy.qos.qos_profile_sensor_data` or equivalent for all
camera topic subscriptions.

### 3.2 Package naming

`gp4_perception` depends on `gp4_interfaces` and `gp4_safety`, but current
branch uses `interfaces` and `safety`. Direct checkout would fail.

**W4 must fix:** Use current package names.

### 3.3 No typed perception interfaces

There are no custom message types for perception. Calibration recorder uses
generic PoseStamped. Object detection uses ad-hoc dict/dataclass patterns.

**W4.T0 must define:** CalibrateHandEye.srv, GetObjectPositions.srv,
CheckCamera.srv, PerceptionStatus.msg (per SUMMARY notes).

### 3.4 No depth-noise or reprojection guard

None of the nodes validate depth measurement quality. In real operation,
D435i depth at close range (<0.5m) can have significant noise, and at far
range (>1.5m, matching clip_distance) the depth becomes unreliable.

**W4 must add:** Depth confidence filtering, per-pixel noise estimation,
and reprojection error checking for fiducial detections.

### 3.5 calibration_date handling

No file hardcodes calibration_date. The extrinsics YAML uses `date: TBD`.
The calibration recorder writes `calibration_status: False`. This is correct
behavior — calibration is never claimed without evidence.

**W4 must maintain:** This invariant. Runtime-fill only, never hardcode.
